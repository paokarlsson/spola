# Round 1 — verdict: FAIL

## Upheld findings (the builder must address these)
- AUD-1 [BLOCKER] framework/modules/http/test/spola/http/TlsMaterialTests.java:101 (`badLength`), reader in Pem.java:160-171 — The "invalid Base64 length" case is flaky, which makes the verification command (criterion 1) and the bad-material table (criterion 7) fail at random. The mutation drops one character, and `Base64.getDecoder()` accepts unpadded input. So whenever the key's DER length is a multiple of 3 (no `=` padding), the corrupted text decodes to garbage and the error comes from key parsing instead. Judge's check: I ran the same mutation on 60 fresh RSA-2048 PKCS#8 keys, and the decoder accepted 21 of them (about 35%). That matches the auditor's red build. Severity stays BLOCKER: the verification command fails about one run in three, so a round cannot be reliably committed green. — fix_hint: make the corruption deterministic and always invalid, for example a body whose total Base64 length is 1 mod 4 (always rejected), or a misplaced `=` mid-stream. Optionally make `Pem` strict per RFC 7468 (length a multiple of 4, padding required) so it reports "not valid Base64" every time. Run the build several times to confirm.
- BRK-1 [MAJOR] framework/modules/http/src/spola/http/ConnectionInput.java:57-72 (deadline turned into a per-read soTimeout), used by Connection over the `SSLSocket` — Over TLS, `headerTimeout`, the idle total and the linger total are no longer limits on total time. One `SSLSocket.read()` blocks inside JSSE until a whole record has arrived, and each underlying TCP read gets the full remaining timeout again. A client that sends one record a byte at a time is never cut off. This breaks the binding mission requirement that limits and timeouts "fungerar som i 07a över SSLSocket". It is also a slowloris hole in code that handles untrusted network input (REGLER §4). Judge's check: I reran `scratch-breaker/exp/Slow.java` against the current `framework/out/spola.http.jar` with a 150 ms byte gap and headerTimeout=1s. Plain HTTP gave `408 after 1016 ms`; TLS gave `200 OK after 9638 ms`. — fix_hint: enforce the header, idle and linger deadlines for TLS connections from the guard thread (as `checkHandshake` does): close the TCP socket underneath when the absolute deadline passes, and don't rely on soTimeout. Add a TLS test that dribbles one request record byte by byte and expects the connection to be cut at about `headerTimeout`.

## MINOR (optional for the builder)
- BRK-2 [MINOR] Connection.java:114-125 and closeSocket():422-434 — `ssl` is set before `in` and `guarded` are created. If `getInputStream()` or `getOutputStream()` throws at that point, `closeSocket()` calls `guarded.guard(...)` on null. The resulting NPE escapes the `finally`, so `connectionEnded` is skipped. Confirmed by reading the code, but not reproduced. The window is narrow (a graceful-stop `closeIfIdle` `shutdownInput` landing right after the handshake), so it is MINOR. — fix_hint: null-check `guarded` in `closeSocket`, or set `ssl` only after the streams exist, and call `connectionEnded` in a nested `finally`.
- BRK-3 [MINOR] TlsMaterial.java:150-160 — An unencrypted PKCS#8 RSASSA-PSS key is rejected with a message that misdescribes it ("is not an unencrypted PKCS#8 RSA, EC, Ed25519 or Ed448 private key"). Supporting PSS is not required by the spec, but the message should be accurate. — fix_hint: name the unsupported key algorithm in the message, or add RSASSA-PSS.
