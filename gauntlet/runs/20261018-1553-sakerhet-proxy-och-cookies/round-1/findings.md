# Round 1 — verdict: FAIL

## Upheld findings (the builder must address these)
- BRK-1 [MAJOR] framework/modules/web/src/spola/web/Sessions.java:73-80 ("the id itself is not kept ... in any field that outlives the response" + "While a request is handled, its id is still in memory as text"); framework/ARCHITECTURE.md:2635-2643 ("i något annat fält som lever efter att svaret byggts" + "Medan en förfrågan hanteras ..."); framework/modules/web/README.md:760-764 ("Medan en förfrågan hanteras finns id:t ändå som text ..."); framework/PROGRESS.md:1011-1013 (P4 entry) — The corrected P4 text still promises more than the code holds, and it does so in the paragraph P4 was meant to fix. After the response, a valid session id stays in live fields of the connection for as long as a keep-alive connection is open: `ConnectionInput.buffer` (byte[8192]) and `ConnectionInput.line` hold the last request's `Cookie`, and the `BufferedOutputStream` buffer of `Connection.wire` holds the last `Set-Cookie`. HTTP/1.1 keep-alive is the default, and Caddy reuses upstream connections, so this is ordinary use and not hostile input. It concerns a security property of the session id. The spec item "Rättade påståenden (P4, P5) ... säger det koden håller" is therefore not met. Verified: I reran the breaker's probe (`scratch-breaker/probe/Heap.java`, `heap.sh`, `heap2.sh`; the scratch sources of http/web/json/util/validation are identical to `framework/`) in my own scratchpad. A live-objects-only heap dump (full GC first) found 2 hits for the id on an idle keep-alive connection after `GET /me` with the cookie, 0 hits after the connection closed, and 1 hit on an idle keep-alive connection after `POST /login` (the id only in the response). The builder made no rebuttal. — fix_hint: Narrow the docs in all four places. Drop "any field that outlives the response" / "något annat fält som lever efter att svaret byggts", or limit it to the session layer (store, `SessionEntry`, `Session`, request state). Say that the id is also in the connection's input and output buffers until the next request on that connection overwrites them or the connection closes (at the latest `idleTimeout` after traffic stops), and that the `String`s stay on the heap until the GC reclaims them. Do not imply that the id is in memory only "while a request is handled". Do NOT clear the buffers in `spola.http`: criterion 2 forbids changes outside `modules/web`, `modules/security-web` and the docs.
