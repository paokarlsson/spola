# Round 1 — verdict: FAIL

## Upheld findings (the builder must address these)
- BRK-1 [MAJOR] framework/modules/security/src/spola/security/BCryptPasswordHasher.java (class Javadoc "Cost"/"Rehashing", `needsRehash`), framework/modules/security/README.md (section "BCrypt och hashar från Spring" and the deviation row "`needsRehash` bara vid lägre kostnad för BCrypt"), framework/PROGRESS.md (known limitations for mission 12), framework/ARCHITECTURE.md:3106-3114 — A stored bcrypt cost above the hasher's cost is never rehashed (`needsRehash` is `stored cost < cost`, as the binding design says), so a known user whose hash came from Spring's `new BCryptPasswordEncoder(12)` costs about 4x the cost-10 dummy hash for ever when the app follows the README and uses `BCryptPasswordHasher.defaults()`. That is a permanent username-enumeration timing oracle. It breaks `Authenticator`'s documented rule "the work is therefore the same as for a known user with a wrong password", and no document warns about it. The only timing limitation that is documented is the one for moving between algorithms. Verified: I compiled the current `src/spola/security/*.java` with the breaker's `Timing.java` probe on JDK 25. Known user with a wrong password took 298-314 ms, unknown user 74-79 ms, five times in a row, and the stored hash stays at `$2a$12$` after a successful login with `users.upgrader(hasher)`. A grep of the Javadoc, README, PROGRESS and ARCHITECTURE finds only "a higher cost gives false", nothing about the timing consequence. Graded MAJOR: this is security-critical code (REGLER §4), an ordinary migration configuration (Spring strength 12 is common), and a documented promise that does not hold. It needs no hostile input. — fix_hint: Documentation only. Do not change `needsRehash` semantics or `Authenticator`, because both are binding decisions in the mission. In the `BCryptPasswordHasher` Javadoc (Cost/Rehashing), in the README section next to the `defaults()` example or in the `needsRehash` deviation row, in PROGRESS.md's known limitations for mission 12, and in ARCHITECTURE.md's cost/`needsRehash` paragraph, say that the default hasher's cost should be at least the highest stored bcrypt cost (for example `BCryptPasswordHasher.of(12)` for hashes from `new BCryptPasswordEncoder(12)`). Also say why: otherwise users with a higher stored cost take measurably longer than unknown users (the dummy hash uses the hasher's cost), and because a higher cost is never lowered, this lasts for good and reveals which usernames exist. If ReadmeTests checks the deviation row's wording, keep its existing expectations unchanged (crit. 2).
