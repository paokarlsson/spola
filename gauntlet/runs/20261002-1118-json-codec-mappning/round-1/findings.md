# Round 1 — verdict: FAIL

## Upheld findings (the builder must address these)
- BRK-1 [MAJOR] framework/modules/json/src/spola/json/codec/Path.java (`isIdentifier` returns false for names longer than `Messages.MAX_EXCERPT`, and `toString` then renders them with `Messages.excerpt`) — Every member-name segment in a path is cut at 40 characters, declared field names included. This breaks the binding decision in mission.md, which says paths use "Samma format och samma escaping" as `spola.json` (`JsonAccessException`/`Paths`), and that code writes the same name in full as `$.name`. Two distinct fields can also end up with the same path, which is not even valid path syntax. I reran the breaker's `Coll.java` against the built jar. The problems for `...Line1` (wrong type) and `...Line2` (missing) both render as `$["shippingAddressAdditionalDeliveryInstruc"... (49 characters)]`, so a client cannot tell which field failed. A developer can hit this in good faith: descriptive field names of 41 or more characters are unusual but legitimate, and uppdrag 08/09 will hand these paths to clients. — fix_hint: Render member names exactly as `spola.json` `Paths` does (identifiers as `.name`, others as escaped `["..."]`) and never cut declared field names. If memory or length has to be bounded for names that come from the document (unknown members, map keys), cut only those, or bound the total message length (`getMessage()` is already capped at 2,000) rather than individual segments. Add a test with a field name over 40 characters that checks the path matches what `JsonAccessException` produces for the same name.

## MINOR (optional for the builder)
- BRK-2 [MINOR] Messages.java:24,138 (`MAX_EXCEPTION_MESSAGE = 200`) — An exception message from app code can carry up to about 185 characters of client input, for example `"not an email: " + value`. The 40-character rule in mission.md is about quoting a value. An exception message is text the developer wrote, and it is escaped (no raw control characters, so no log forging), cut ("avkortade", criterion 8), and documented as a deliberate choice. Kept MINOR. Either tighten it to 40, or state explicitly in ARCHITECTURE.md/README that the 40-character limit does not cover exception text.
- BRK-3 [MINOR] JsonCodecs.java (`JSON` identity codec) and the "Depth" Javadoc in JsonCodec.java — The identity codec does not count depth. Reproduced: a 100,000-deep `JsonArray` decodes and writes without error, and there is no `StackOverflowError`. The mission's depth decision does name "träd byggda i kod", but this only shows up with a tree deeper than 512 that was built in code. Trees from `read` are already bounded by the parser. Severity is MINOR because it needs pathological input and does not crash. Either count depth in `JSON` (iteratively) or narrow the Javadoc.
- BRK-4 [MINOR] JsonCodecs.java, BIG_INTEGER/BIG_DECIMAL encode — Encode allows up to 10,000 digits (BIG_DECIMAL has no precision bound at all), but `read` uses `JsonLimits.DEFAULT.maxNumberLength` = 1,000. As a result, `read(write(v))` fails for numbers with 1,001 to 10,000 digits. Such values are rare in normal use. Either align the bounds with `maxNumberLength` or document the asymmetry.
- MNT-1 [MINOR] JsonCodec.java `object(...)` overloads and `Constructors.Of1..Of16` — These are about 700 lines of mechanical code with no note on how they were made or that they must be changed together. Add a comment, a consistency test, or the generator.
- MNT-2 [MINOR] LazyCodec.java:46-56 — `enterLazy`/`exitLazy` are not in try/finally. This is correct only because the state is per call and is abandoned on an exception. Add a comment saying so, and consider moving `Encoding.lazyLoop()` to a shared place.
- MNT-3 [MINOR] JsonTests.java:29-30 — The comment exists but does not say why the reference is fully qualified (Build.java allows one test entry per module). Expand it by one line.
