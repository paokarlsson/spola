## Upheld findings (the builder must address these)
- BRK-1 [MAJOR] framework/modules/web/src/spola/web/SessionState.java:74-90 (`renewFor`: `current.entry().leave(current)`, then `owner.limit(...)`, then `renew()`), together with `renew()`'s fallback to `create` when the view is stale (lines 54-67) — A login of user U on cookie S takes S out of U's index (`user = null`) before it renews S. If another request renews S with the public `Sessions.renew` in that window, the login's view goes stale and it creates a different session, and only that one is counted. S stays logged in (its `LOGGED_IN` attribute is unchanged) but is never in the name → sessions index again. The limit no longer applies to it (G1). A later login by another user treats it as anonymous and keeps its attributes (G2). Reproduced: with limit 10 and 1500 rounds, 77 working sessions for one user remain after more logins, and the next user inherits the note in 67 of them. This is session and authentication code where an attacker controls the timing of two requests on their own cookie (judge rule 6 exception, mission "konstruerad indata räknas som realistisk"). Repeated, it brings back the original G1 lockout. It also breaks the documented promise that the count is at most the limit once logins finish (PROGRESS/ARCHITECTURE, `Sessions` Javadoc "Sessions per user"). The precondition is ordinary use of the documented `Sessions.renew` ("call it when the session changes privilege"). — fix_hint: Do not let a session being logged in drop out of the index through a field that a concurrent renew of the same entry can leave null for good. Options: keep `user` set and protect the session in `limit` another way (pass its entry as `keep` in the pre-trim, or mark it "logging in" so that `limit` skips it), or make the renewed or created session's ownership not depend on which request happened to renew it. Whatever the mechanism, after all requests finish every live session holding a login for U must be in U's index, so the count is ≤ the limit. Keep the guarantee that a concurrent login of the same user never ends the session being logged in, or document why it changes. Add a regression test through a real `HttpServer`: a login racing `Sessions.renew` on the same cookie, many rounds, then assert at most `limit` working sessions and that another user's login over each of them sees no attribute. Make sure BRK-2's case is covered as well.

## Rejected
- AUD-1 — Not a defect. The requirement's governing sentence is "svaret ska inte kunna sparas av en delad cache". A bare `max-age=60` or `no-cache` on a `Set-Cookie` response would let a shared cache store it, so the stricter rule fulfils the requirement rather than going against it. The spec's Antaganden allow motivated deviations, and this one is motivated in build.md and ARCHITECTURE.md. The changed `CsrfCookieTests` expectation is named in build.md, as AC2 requires. AC6 is met. Ruling for later rounds: the stricter G3 rule is accepted.
- AUD-2 — Not a defect. G4 follows the spec literally ("Ett värde som handlern satt behålls, utom att `public` och `s-maxage` ersätts"), and the leftover `max-age` risk is documented. Ruling for later rounds: keeping a handler's `max-age=60` on a logged-in response without a cookie meets the spec, and widening it would go beyond the contract.

## Duplicates
- (none) BRK-2 has the same root cause as BRK-1 but a different effect (a G2 failure from concurrent logins by two different users), so it is kept as its own MINOR below.

## MINOR (optional for the builder)
- BRK-2 [MINOR] SessionState.java:78 (`before = pendingUser != null ? pendingUser : current.user()`) — If anna logs in again while bertil logs in at the same moment with anna's cookie, anna's `leave` can null `before`. Bertil then renews anna's session and keeps her attributes (reproduced: 46 of 1500 rounds at limit 1000). Severity stays MINOR: the only party who could trigger this already holds anna's cookie and so already has her session, which makes it a rare good-faith concurrency case, not an escalation. The fix for BRK-1 should cover it. Add it to the race test.
- MNT-1 [MINOR, downgraded from MAJOR] spola.web `CacheControl` vs `WebSecurity.CacheControl` — The parser is duplicated, and the security-web copy is tested with a smaller table (it lacks an escaped quote, an open quote, an empty argument and `=private`). Downgraded because there is no behavioural defect: the copies are identical today (judge diff above). The input is the app's own response header, not data from outside the process, so the §4 exception does not apply. The parser fails closed (malformed → `no-store`). The duplication is a documented choice to keep spola.web's public API minimal, as the spec asks. Cheap improvement: run `SessionCacheTests`' case table against the security-web copy too (through `XSRF-TOKEN` and `forIdentity`). A new public helper in `spola.web` would widen the public API that the spec wants kept minimal.
