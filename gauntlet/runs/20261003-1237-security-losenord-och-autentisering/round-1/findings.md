# Round 1 — verdict: FAIL

## Upheld findings (the builder must address these)
- BRK-1 [MAJOR] framework/modules/security/src/spola/security/Authenticator.java:117-123 + InMemoryUserStore.java (updatePassword), with the documented wiring `Authenticator.of(store, hasher, store::updatePassword)` — A hash upgrade overwrites the stored hash unconditionally. A login that verified the OLD password and is still computing the rehash (one full `defaults()` hash, ~125 ms) writes a fresh hash of the old password over a password change made in the meantime (lost update): the password change is silently undone and the old (possibly leaked) password works again. Judge reran `scratch-breaker/Exp.java` against `out/spola.security.jar` and reproduced: "new password: Failed[BAD_CREDENTIALS]", "old password: Authenticated". This needs only ordinary concurrency (a login on one device while the password is changed on another, during hash migration), not hostile input, and it is security-critical code (REGLER §4), so MAJOR stands. The mission fixes the `PasswordUpgrade` signature `void upgrade(String username, String newHash)`, so the fix must keep that signature. — fix_hint: Keep the public signatures from mission.md. Make the recommended InMemoryUserStore upgrade path conditional and atomic. For example, add a store-provided `PasswordUpgrade` (e.g. `InMemoryUserStore.upgrader(PasswordHasher)` or a conditional `upgradePassword`) that inside `computeIfPresent` replaces the hash only if the current stored hash still `needsRehash` (a hash set by a password change with current settings is then never overwritten). Or use another compare-and-set that can be shown to be equivalent. Use it in README, LoginExample and the Javadoc instead of `store::updatePassword`. Add a deterministic test: block the upgrade, change the password, release, and assert that the new password works and the old one fails. Also document in the `PasswordUpgrade` Javadoc and in ARCHITECTURE "Säkerhet del 1" that custom stores must make the upgrade conditional for the same reason. Keep criterion 7 green (exactly one `upgrade` call, and no further call after the upgrade).
