# Round 1 — verdict: FAIL

## Upheld findings (the builder must address these)
- BRK-1 [MAJOR] `Connection.exchange` (Connection.java ~133-191) and `MalformedRequestTests` BODY_CASES. When a handler does not read a chunked body with broken framing, the server sends the handler's response (e.g. `200 OK` with no `Connection: close`) and only finds the framing error afterwards in `skipRest()`. Criterion 5 requires "exactly the expected status, `Connection: close`" for chunk-size errors and a missing CRLF after chunk data, and this breaks it. I reproduced it: `java -p framework/out/spola.http.jar --add-modules spola.http round-1/scratch-breaker/exp/Chunk.java` gives `HTTP/1.1 200 OK ... deleted`, EOF, handler calls = 1. The tests miss it because their handler always calls `request.bytes()`. The scope is narrowed, see the ruling under Rejected: the "handler is never called" part of criterion 5 is not upheld for errors that sit in the body itself. The binding mission design (a lazy body, `100 Continue` only on first read, "chunked över gränsen: läsningen kastar och servern svarar 413 om svaret inte börjat") means body framing can only be found while the body is read, so the builder's decision 2 stands for that part. The upheld part is that the server commits a response that looks successful without checking the framing of a request it still has to consume. This is protocol parsing of untrusted input (REGLER §4), so crafted input is realistic. — fix_hint: for responses that are not streamed, and when no `100-continue` is pending, skip and validate the unread rest of the body (within `maxBodySize`/`readTimeout`) before writing the response head. On a framing error, send the body failure's status (400/413) with `Connection: close` in place of the handler's response. A streaming response, or an unread body under `Expect`, may keep the current behaviour (close after the response), but document it. Add BODY_CASES variants with a handler that never reads the body, and assert the exact status and `Connection: close`.
- BRK-2 [MAJOR] `HttpServer.close()` (synchronized; `joinUninterruptibly(connection.thread())` at HttpServer.java:251/269). An external `close()` (a shutdown hook or try-with-resources) and a handler's own `close()` deadlock. The Javadoc explicitly allows the handler's call ("A handler may call close() itself"). The handler blocks on the monitor, where an interrupt cannot reach it. The first `close()` aborts it after `shutdownTimeout` and then joins it with no time limit, so `close()` never returns, against criterion 13 and the mission's "avbryter det som återstår efter shutdownTimeout". I reproduced it with `scratch-breaker/exp/Deadlock.java`: "close() returned within 10 s (shutdownTimeout 1 s): false", stuck at HttpServer.joinUninterruptibly:269 <- close:251. A /shutdown endpoint plus SIGTERM is ordinary concurrency, so MAJOR. — fix_hint: do not hold a monitor across the joins. Mark "closing" with an AtomicBoolean/CAS and use a latch for "closed". A second caller on a connection thread returns at once (its response gets `Connection: close`), and a second caller elsewhere waits on the latch. Add a test with a concurrent external and in-handler `close()`.

## Rejected
- BRK-1 (the "handler is never called" part, for body-level chunked errors) — this conflicts with the binding mission design decisions (lazy body, 100-continue on first read, 413 from the read for chunked bodies over the limit). The builder documented it (decision 2), and the 71 head cases assert that the handler call count is 0. The upheld part is above.
- AUD-1 — `chunked, identity`/`xchunked`/`identity` give 400, not the 501 the mission names. RFC 9112 §6.3 says the server "MUST respond with the 400 (Bad Request)" when chunked is not the final coding, and REGLER §4 (tested against official specifications) outranks the mission's wording. The builder documented it in README/ARCHITECTURE, and the connection closes in every case. No action.

## MINOR (optional for the builder)
- BRK-3 [MINOR] `Connection.closeSocket()` skips the linger while `server.closing()` is true. A request still running at a graceful stop, with unread pipelined input or an unread body, can have its `Connection: close` response destroyed by an RST (RFC 9112 §9.6). It needs pipelining or an unread body at the exact moment of shutdown, so MINOR. — fix_hint: linger while closing too, bounded by what is left of `shutdownTimeout`.
- AUD-3 [MINOR] `requires static java.net.http` in `module-info.java` exists only for the tests. It is allowed (a JDK module, criterion 2 met, `SourceRulesTests` polices main code). Optional: a test-only read edge in `Build.java` later.
- MNT-1 [MINOR] `Connection.exchange` mixes too many jobs. Extract `shouldClose(...)` and the handling of a body-writer failure. Worth doing together with the BRK-1 fix.
- MNT-2 [MINOR] `Connection.guarded` (and `in`/`wire`/`writer`) is set in `run()`, and the guard thread reads `guarded` without `volatile`. In theory the guard could keep seeing `null` and the write timeout would never fire. Make it `volatile` or create it in the constructor.
- MNT-3 [MINOR] The state transitions (`compareAndSet` combinations) are not documented. Add a transition table to the `State` Javadoc.
- MNT-4 [MINOR] There are two `closeQuietly` helpers. Merge them.
