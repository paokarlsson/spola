# Round 1 — verdict: FAIL

## Upheld findings (the builder must address these)
- BRK-1 [MAJOR] framework/Build.java `runTests` (tests run in the build JVM) + framework/modules/test/src/spola/test/Runner.java — A test that calls `System.exit(0)` ends the build with exit 0. There is no summary and no BUILD OK/RED line, later tests in the same suite (including failing ones) never run, and other modules' tests are skipped. Judge reproduced this in a copy (/tmp/jdg/fw): a suite with `test("exit", () -> System.exit(0))` followed by `test("fail", () -> assertEquals(42, 41))` gave `exit=0`, and the output stopped after the suite header. This violates the spec requirement "Build.java ... fails if any test fails" (AC3). The verification gate goes silently green. build.md lists it as a "known gap", but that is not a rebuttal. The spec's assumptions only allow abandoned daemon threads, not an early exit that reports success. A good-faith developer testing a CLI `main()` can plausibly trigger it, so it stays MAJOR. — fix_hint: Fail closed. The simplest option is a shutdown hook in Build.java that calls `Runtime.getRuntime().halt(1)` (with a message) unless the build reached its own final `System.exit`. Alternatives are running each module's tests in a child JVM and requiring an explicit completion marker, or exit code 0 together with a printed summary. Add a test or build-level check that proves an exiting test gives a red build.
- BRK-2 [MAJOR] framework/modules/test/src/spola/test/Assertions.java:83 `assertNotEquals(Object, Object)` — With no primitive overloads, `assertNotEquals(0, someLong)` compares `Integer` with `Long` and always passes. That is a false green on an ordinary call. Judge reproduced it: `assertNotEquals(0, 0L)` reported `ok`. A false green in the core assertion library undermines every test written with it, and the call shape (`assertNotEquals(0, Files.size(p))`) is common. (`assertEquals(0, 0L)` fails safely and shows the classes, so only the "not equals" direction is unsafe.) — fix_hint: Add `assertNotEquals(long, long)` and `(double, double)` overloads (plus `assertEquals(long, long)` for symmetry), and/or make `assertNotEquals` fail or refuse when both arguments are `Number`s of different boxed classes. Add a regression test for `assertNotEquals(0, 0L)`.

## Rejected
- AUD-1 — Not a defect. The entry is named explicitly in Build.java, and the test classes are compiled into a separate layer that the build script cannot reference at compile time, so resolving one named class/method reflectively is unavoidable. That is consistent with REGLER §4 ("where it can be avoided"). There is no scanning and no naming convention. The auditor itself requests no fix.
