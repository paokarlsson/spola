# Säkerhetsgranskning 2026-10-18

Granskningen gjordes av fem AI-granskare (inte av en människa), en per område, mot koden från
uppdrag 11a–14 på grenen före release 0.2.0. Varje fynd är verifierat med en prob mot de byggda
jar-filerna eller med exakt resonemang i koden. Ingen granskare hittade något CRITICAL eller HIGH.
Rättningarna är uppdragen 15a–15d. **Det här ersätter inte en mänsklig granskning** av de
säkerhetskritiska modulerna.

| Område | Moduler | Högsta fynd | Uppdrag |
|---|---|---|---|
| Sessioner | `spola.web` | MEDIUM (ett konto kan fylla `maxSessions`) | 15a |
| Inloggning och CSRF | `spola.security.web` | MEDIUM (samma) | 15a, 15b |
| Lösenord | `spola.security` | LOW | 15c |
| Proxyhuvuden | `spola.web`, `spola.http` | LOW | 15b |
| REST-klient | `spola.client` | MEDIUM (Bearer-nyckeln läcker vid eko) | 15d |

Verifierat utan fynd, i korthet: inga sätt att kringgå autentisering, behörighetsregler eller CSRF;
ingen session fixation; sessions-id med 256 bitar och uppslagning på SHA-256; bcrypt stämmer mot
libxcrypt i över 1 200 fall åt båda hållen; `IpLiteral` och CIDR-matchningen gav 0 avvikelser i 6
miljoner respektive 200 000 differentiella fall; inga omdirigeringar, ingen proxy och full
TLS-verifiering i klienten; ingen korskommunikation mellan förfrågningar på en delad klient.

## Sessioner
Sessions review: nothing HIGH/CRITICAL.
S1 MEDIUM Sessions.create + WebSecurity.login: global maxSessions (10 000) full => 503; one client (one account logging in repeatedly, or an anonymous getOrCreate route) can block all other logins and keep them blocked by touching sessions within 30 min. Probe: 10 000 logins by one account in 10.9 s, then another user's login gets 503. Fix: cap sessions per identity in login (drop that user's oldest, like Spring maximumSessions), or evict sessions without login before refusing a login / separate limits; at minimum document + recommend rate limiting.
S2 LOW Sessions.create:459-464: limit-path cleanup not guarded against parallel runs (minute sweep is CAS-guarded); each refused request in the meantime walks the whole store. Fix: CAS/tryLock in-progress flag; losers answer 503 without walking.
S3 LOW SessionState.finish:91-93: no-store added only when Cache-Control is missing; a handler's "public, max-age" or s-maxage on a session-setting response stays shared-cacheable. Fix: when a session Set-Cookie is added, override shared-cache directives (force private/no-store).
S4 LOW WebSecurity.login: logging in as B over A's live session renews but keeps A's attributes. Fix: if the session holds a different identity, invalidate and create a fresh session.
S5 LOW Sessions Javadoc/ARCHITECTURE: "a memory dump holds no valid ids" overstated. Reword to "the store holds only hashes of ids".
Hardening (not findings): no absolute timeout; SESSION without __Host- allows cookie tossing (docs recommend __Host-); no Cache-Control on authenticated responses without cookie (Spring adds no-cache headers by default).

## Inloggning och CSRF
Login/CSRF review: nothing HIGH/CRITICAL; no auth/authz/CSRF bypass, no fixation, fail-closed errors.
W1 MEDIUM (same as sessions S1): one account can block all logins by filling the global maxSessions; 300 logins in 1.4 s in probe, then anna's login -> 503 and anon /cart -> 503. Fix: per-identity cap in WebSecurity.login (end that user's oldest session, like Spring maximumSessions(n)); consider absolute lifetime.
W2 LOW Sessions.lookup:393-403 first live value wins + default name SESSION: cookie tossing from a sibling subdomain plants attacker's logged-in session with Domain=parent; Path=/api -> victim uses app as attacker. Probe: victim sends [mallory(path=/api), anna] -> me=mallory. Fix: document __Host-SESSION + secure(true) as production choice; optionally treat a request whose cookies resolve to more than one live session as anonymous.
W3 LOW (same as sessions S4): login as a different user keeps previous user's session attributes. Probe: mallory sees anna's note. Fix: in login, if session holds a different LOGGED_IN identity, invalidate and create fresh.
W4 LOW WebSecurity:528: authenticated responses get no Cache-Control (Spring adds no-cache, no-store, max-age=0, must-revalidate by default). Fix: in authorize, when identity present and no Cache-Control, add Cache-Control: no-store; when the filter sets a cookie, override public with private/no-store.
Note: CSRF token rotation is cosmetic (stateless double submit; pre-login token still accepted). Sound as "same-origin custom header required". Optional defense in depth: bind token to session (HMAC of session id).

## Lösenord
Password hashing review: nothing CRITICAL/HIGH/MEDIUM. bcrypt verified against libxcrypt (1 260 cases both directions).
F1 LOW InMemoryUserStore:90 / PasswordUpgrade:26 / Authenticator:124-126: upgrade only checks "still needs rehash", not "still the verified hash"; a password change written with older settings during an in-flight upgrade is overwritten with a hash of the OLD password (rolling deploy raising cost). Probe Race.java: old password Authenticated, new password BAD_CREDENTIALS after change. Fix: compare-and-set on the verified hash: PasswordUpgrade.upgrade(username, verifiedHash, newHash); InMemoryUserStore computeIfPresent(... equals(verifiedHash) ? new : u); document SQL "WHERE username=? AND hash=?".
F2 LOW Authenticator:118: a known user with an unparsable stored hash makes matches throw IAE -> 500, unknown users -> 401: username enumeration with one request (e.g. leftover {noop}/{sha256}/{MD5}/Spring hex {pbkdf2} rows after Spring migration). Fix: catch IAE from matches for a found user, run the dummy check, log WARNING with class name only, return BAD_CREDENTIALS.
F3 LOW BCryptPasswordHasher:189-191 + Delegating: Authenticator's "unknown users cost the same" doesn't hold across algorithms; >72-byte passwords are refused by bcrypt at zero cost while {pbkdf2} users cost 170 ms -> noise-free signal. Fix: caveat in Authenticator/delegating Javadoc; optionally dummy check with the slowest delegate.
F4 LOW Pbkdf2PasswordHasher:75,130: hashBytes 33-64 doubles server cost but not attacker cost. Fix: cap new hashes at 32 bytes, keep parsing up to 64, needsRehash moves them.

## Proxyhuvuden
Proxy headers review: nothing CRITICAL/HIGH/MEDIUM. 6M IpLiteral and 200k CIDR differential cases, 0 mismatches.
P1 LOW ForwardedHeaders:146-150 -> Sessions:554-555 / Csrf:294-295: a trust mismatch (e.g. TrustedProxies.of("172.18.0.5") with a stale Caddy address, IPv6 path) silently drops Secure from SESSION and XSRF-TOKEN, nothing logged. README says secure(true) only needed without ForwardedHeaders. Fix: (1) guidance: recommend withCookie(c -> c.secure(true)) for sessions and CSRF in any HTTPS-only deployment; (2) optionally: ForwardedHeaders logs one WARNING per instance the first time an untrusted sender sends X-Forwarded-Proto/For (peer address only, never values).
N3 (docs): README example WhoamiApp (and the Caddy snippets in security-web README) bind loopback via HttpServerOptions.DEFAULT; Caddy in another container cannot connect. Bind 0.0.0.0/:: in the Docker example.
N1/N2 (docs, already documented): privateNetworks() trusts every container; docker-proxy may hide the client; never treat a private client address as authorization.

## REST-klient
Client review: nothing HIGH/CRITICAL.
SEC-1 MEDIUM RestRequest.secrets:221-242: only whole header values hidden; a server echoing just the token after "Bearer " (or "bearer ", or decoded Basic user:password) leaks the key into getMessage/toString/stack trace. Fix (verified green in scratch build): for Authorization/Proxy-Authorization also add the credentials after the first space (stripped), and for Basic also the Base64-decoded user:pass and the password; Causes.textIsSafe reads the same list. Test: Failures kind "a 401 that names the bearer token on its own" in SecretTests.RESPONSE_ECHOES with AUTH_MARKER. Docs: README:239-240 + Javadoc. Optional: each query parameter value raw and percent-decoded.
SEC-2 LOW README:197-203, :228, RestClientException:17: recommended log line logs raw bodyExcerpt() with comment "aldrig nyckeln" -> hides nothing. Fix: examples log e.getMessage(), or expose the hidden excerpt (e.g. safeExcerpt()) and use it.
SEC-3 LOW RestClient:102 / README: -Djdk.httpclient.HttpClient.log=headers|requests|all and jdk.internal.httpclient.debug print header values and queries. Fix: document never to enable in production (optionally refuse in build()).
SEC-4 LOW Uris.pathProblem:82-112 and baseProblems:59-64: "." and ".." segments (also %2e) pass and are sent raw; URLEncoder.encode("..") == "..", so encoded ids can reach parent resources with the app's credentials. Fix: refuse dot segments (after %2e/%2E -> .) in path and base, Javadoc sentence.
BRK-2 (round 2, docs): spola.json cause quotes up to 40 chars per value in up to 100 problems (+200 of an exception message), not "up to 40 characters".
